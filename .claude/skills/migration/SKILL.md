# Миграции

База — SQLite в томе, живых данных немного, но они настоящие: результаты
студентов за семестр. Откат кода схему не откатывает, поэтому цена ошибки
здесь выше обычной.

## Как сделать

1. Поправить `app/models.py`.
2. Написать миграцию руками в `migrations/versions/NNNN_описание.py` —
   автогенерация тянет лишнее. Соседние файлы показывают стиль: ревизия,
   `down_revision`, `upgrade`, `downgrade`.
3. SQLite не умеет `ALTER TABLE DROP COLUMN` — только `op.batch_alter_table`,
   он пересоздаёт таблицу.
4. Прогнать с нуля и проверить схему:
   ```bash
   T=$(mktemp -d) && SECRET_KEY=x DATA_DIR=$T alembic upgrade head
   sqlite3 $T/sport.db "select name from pragma_table_info('таблица');"
   ```
   Путь к базе берётся из `DATA_DIR`, переменная `DATABASE_URL` тут не при делах.
5. `pytest -q` — тесты гоняются на свежей схеме из моделей, поэтому расхождение
   моделей и миграции они не поймают. Пункт 4 обязателен.

## Репетиция на боевых данных

Если миграция трогает существующие строки (переносит данные, удаляет колонку,
пересоздаёт таблицу, на которую ссылаются другие) — сначала прогнать на копии:

1. Снять копию боевой базы в `$T/sport.db` — как именно, зависит от стенда
   (в рабочем репозитории МГУ — навык `msu-deploy`, «Копия боевой базы»).
   Это чтение данных студентов: только с согласия того, кто отвечает за прод.
2. Прогнать миграцию на копии и проверить целостность:
   ```bash
   SECRET_KEY=x DATA_DIR=$T alembic upgrade head
   sqlite3 $T/sport.db "pragma integrity_check; pragma foreign_key_check;"
   ```

Сверить количество строк в основных таблицах до и после. Копию боевых данных
после репетиции **удалить** — в ней имена студентов.

## После выкатки

Выкатка сама делает копию базы в `/data/backup-*.db` до миграции. Проверить
на сервере версию схемы, счётчики и `integrity_check` — по навыку выкатки
своего стенда (в рабочем репозитории МГУ это `msu-deploy`).

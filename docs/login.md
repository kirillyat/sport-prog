# Вход и аккаунты

Как люди входят на портал и как портал узнаёт их аккаунты на площадках.
Что создать в Authentik на стороне администратора — в
[DEPLOY.md](../DEPLOY.md#3-authentik--что-создать-и-что-вернуть).

---

## Настройка Telegram

1. Создай бота у [@BotFather](https://t.me/BotFather), получи токен.
2. Узнай свой telegram id: отправь боту `/id` (или спроси у [@userinfobot](https://t.me/userinfobot)).
3. Заполни в `.env`:

```
TELEGRAM_BOT_TOKEN=123456:AA...
TELEGRAM_BOT_USERNAME=my_sport_bot     # без @
TEACHER_TELEGRAM_IDS=123456789         # тебе выдастся роль преподавателя
```

Бот работает на long polling — публичный домен и HTTPS не нужны.
Штатный Telegram Login Widget их бы потребовал, поэтому вход сделан через бота:
страница выдаёт одноразовый код, ты отправляешь его боту, страница сама открывается.

`TEACHER_TELEGRAM_IDS` применяется при каждом входе, так что роль преподавателя
нельзя потерять, даже если что-то нажать в интерфейсе. Свой id узнаешь, отправив
боту `/id`. Взят именно id, а не `@username`: логин можно сменить, а
освободившийся — занять кому угодно.

## Вход через Authentik (OpenID Connect)

Третий способ входа рядом с Telegram и dev-формой. Подходит любой провайдер
с OIDC discovery — Authentik, Keycloak, Authelia.

В Authentik: **Applications → Providers → Create → OAuth2/OpenID Provider**.
Тип клиента — Public (тогда работает чистый PKCE) или Confidential (тогда
впиши секрет). Redirect URI — `<BASE_URL>/login/oidc/callback`. Скоупы —
`openid profile email`; чтобы роль преподавателя выдавалась по группе,
включи в провайдере scope mapping для `groups`.

```
OIDC_ISSUER=https://auth.example.org/application/o/sport/
OIDC_CLIENT_ID=...
OIDC_CLIENT_SECRET=          # пусто для public-клиента
OIDC_TEACHER_GROUPS=sp-teachers
```

Что происходит при входе: Authorization Code + PKCE, `state` и `nonce`
живут в подписанной cookie 10 минут, код обменивается по бэкенд-каналу,
профиль берётся с userinfo. Пользователь привязывается по `sub` — стабильному
идентификатору провайдера, а не по email.

**Роль.** Если пользователь состоит хотя бы в одной из `OIDC_TEACHER_GROUPS`,
при каждом входе он получает роль преподавателя. Автоматического понижения нет:
роль могла быть выдана иначе (первый вход, вручную).

**Честно про проверку токена.** Подпись ID-токена локально не проверяется —
в зависимостях нет JWKS-парсера. Это безопасно, потому что токен приходит
напрямую от провайдера по TLS в обмене кода, а не от браузера; `nonce`
сверяется. Если провайдер окажется за недоверенным прокси — добавь проверку
подписи (PyJWT + cryptography) поверх `app/oidc.py`.

## Один участник — несколько способов входа

Войти можно через Telegram или через Authentik. Чтобы это был **один человек
на портале**, а не два, второй способ привязывается из личного кабинета:
`/accounts` → «Способы входа» → «Привязать».

- Вошёл через Authentik → привязал Telegram: получил уведомления о заданиях.
- Вошёл через Telegram → привязал Authentik: сможет входить учётной записью
  факультета, история и баллы останутся.

Привязку завершает тот же браузер, который её начал — чужим кодом прицепить
свой Telegram к чужой учётке нельзя. Если этот Telegram или аккаунт провайдера
уже принадлежит другому участнику, привязка отклоняется.

Отвязать можно любой способ, кроме последнего: иначе человек потеряет доступ.

## Кто считается студентом портала

Telegram — способ связи, а не удостоверение: бота может завести кто угодно.
Студенчество подтверждает учётная запись факультета через Authentik.

| | Вход только через Telegram | Есть учётная запись факультета |
|---|---|---|
| Войти и осмотреться | да | да |
| Привязать Codeforces и LeetCode | да | да |
| Вступить в группу | нет | да |
| Клубные задания и табло | нет | да |

Отвязка работает по тому же правилу:

- **Codeforces и LeetCode** отвязываются в любой момент — это просто аккаунты
  на площадках.
- **Telegram** отвязывается, только когда привязана учётная запись факультета.
  Иначе входить будет нечем.
- **Учётная запись факультета** не отвязывается совсем: отвязали бы — человек
  остался бы в группах, перестав быть подтверждённым.

Пока `OIDC_ISSUER` пуст, проверять нечем и портал работает как раньше: Telegram
даёт полный доступ. Это же спасает локальную разработку.

Преподаватель видит отметку «подтверждён» в списке студентов и сразу понимает,
кто вошёл через организацию, а кто зашёл с улицы.

## Как студент привязывает аккаунт

Портал не просит пароли и токены — только подтверждение, что профиль твой:

1. Студент вводит хэндл на `/accounts` и получает код вида `algo-a1b2c3d4`
   (приставка — `VERIFICATION_PREFIX`; код видят все, кто откроет профиль).
2. Вписывает код в профиль на платформе:
   - **Codeforces** — Settings → Social → поле «Organization» (или «First name»);
   - **LeetCode** — Edit Profile → поле «Name» (или «Summary»/«Website»).
3. Жмёт «Проверить». Портал читает публичный профиль и находит код.
4. После подтверждения код можно убрать.

## Что видно на каждой платформе

| | Codeforces | LeetCode |
|---|---|---|
| API | официальный публичный | неофициальный GraphQL |
| Каталог задач | весь, с рейтингом и тегами | весь, со сложностью и тегами |
| История посылок | полная, включая неудачные попытки | **только последние 20 принятых** |
| Авторизация | не нужна | не нужна |

Полная история LeetCode доступна только по сессионной куке `LEETCODE_SESSION`,
а это фактически полный доступ к аккаунту студента. Сознательно **не** запрашиваем:
для задачи «кто решил назначенное» хватает публичных данных, а хранить чужие
сессии — ответственность, которой лучше не брать.

Практическое следствие: синкер ходит на LeetCode каждые 10 минут, и пока студент
не решает больше 20 задач за этот интервал, ничего не теряется. Неудачные попытки
на LeetCode не видны — аналитика «кто застрял» работает только по Codeforces.

При первой синхронизации Codeforces подтягивается до 3000 последних посылок,
дальше — только свежие.
